#+title: DiemBFT v4

An implementation of the DiemBFT v4 pseudocode, section 3 of the paper. It
commits on a contiguous 2-chain. =PSEUDOCODE.org= maps each procedure onto the
code.

* The tree

The package works directly on the generated =diempb= messages, which are
read-only once built. Rounds are =uint64=, replica ids =uint32=, hashes
32-byte slices.

One file per module of the paper's section 3.

#+begin_example
diem/
  core.go          3.1 Main — one method per input
  ledger.go        3.2 Ledger — speculative execution over a branching state
  blocktree.go     3.3 Block-tree — pending blocks, vote buckets, QC formation
  safety.go        3.4 Safety — the voting rules and their two counters
  pacemaker.go     3.5 Pacemaker — round advance, timeouts, TC formation
  leader.go        3.7 LeaderElection — round-robin, two rounds per leader
  verify.go        everything checked before a message reaches the core
  types.go         NewBlock; the helpers over a single message are methods in
                   proto/diempb/methods.go
  seams.go         3.6 MemPool, Transport, Crypto, Clock and SafetyStore:
                   what the core plugs into
  quorum.go        Faulty(n), QuorumSize(n)
  hash.go          ExecuteHash, the default execution; the message digests
                   are methods in proto/diempb/hash.go
  genesis.go       the fixed genesis block and its certificate
  sim_test.go      the deterministic multi-replica harness
  fakes_test.go    stand-in signer and hand-driven clock for the tests

diemnet/           the Gorums layer; may import Gorums and protobuf
  gorums.go        the Transport: outbound calls into Gorums' send queues
  server.go        inbound handlers; verifies at the edge, then calls the
                   core under the replica's lock

proto/diempb/
  diem.proto       the wire messages and the Gorums service
  *.pb.go          generated by protoc-gen-go and protoc-gen-gorums

replica/replica.go wires Core + Transport; owns the lock and the lifecycle
#+end_example

* Where the protocol lives

The algorithm is the =Safety= module plus the commit rule; everything else is
plumbing around them.

- The whole protocol surface — =core.go:OnProposal=, =OnVote=, =OnTimeout=
  and =OnBlock=, one method per input
- Voting rules — =safety.go:safeToVote= and =safeToTimeout=, both resting on
  =consecutive=
- Commit rule — =safety.go:commitStateIDCandidate=: a block whose round
  directly follows its parent's carries the parent's speculated state, so the
  quorum certifying the block also certifies that commit. That is the 2-chain
  rule
- Certificate formation — =blocktree.go=, =ProcessVote=
- Round change — =pacemaker.go= in full
- Leader selection — =leader.go=, round-robin only; the paper's reputation
  scheme is left out (=PSEUDOCODE.org=, 3.7)
- Checked before anything touches state — =verify.go=

* Verification

The rule is *authenticate at the edge, authorise by state in the core.*

Signatures, quorum sizes, certificate well-formedness and signer ordering are
checked by =Verifier=, called from =diemnet/server.go= on the handler
goroutine, and anything that
fails is dropped before it reaches the core. What stays in =Core= is what depends on
this replica's current beliefs: whether the sender leads this round, and
whether the message is too far ahead to buffer.

Who leads a round is a function of the round alone (=leader.go:GetLeader=), so
the sender and author checks could move to the edge. They stay in =Core= next to
the round check, which does need this replica's round, because the paper puts
all three in =process_proposal_msg= (=core.go:OnProposal=).

=core.go= therefore holds exactly one crypto call — =Sign=, when this replica
proposes. =Safety= re-verifies nothing. It shares the process and the key with
the rest of the replica, so it trusts what the edge checked
(=PSEUDOCODE.org=, =valid_signatures=).

* Interfaces

This package declares five, all in =seams.go=, and each has a real
implementation and a test one: =MemPool= (=replica.Payload= and =fifoPool=)
supplies a leader's payload, =Transport= (=diemnet= and the sim's in-memory
network) is the hand-off out of the core, =Crypto= (=diemcrypto= and
=testSigner=) signs and verifies digests as plain bytes, with the signer id as an
argument — it knows nothing of the message types, and checking a certificate is
=verify.go:VerifyQC= and =VerifyTC= in =diem=, which hand its signatures to
=VerifyAll= as one batch — =Clock= (=SystemClock= and =fakeClock=)
arms the round timer, and =SafetyStore= (=replica.fileStore= and =memStore=) saves
=Safety='s counters before a vote or timeout leaves.

The ledger, the block tree and the round timer are concrete
types, called directly. An interface with a single implementation is a hop to
step through while reading and buys nothing.

* How it uses Gorums

=proto/diempb/diem.proto= defines four RPCs:

#+begin_example protobuf
rpc Proposal(ProposalMsg)   returns (Empty) { option (gorums.multicast)  = true; }
rpc Vote(VoteMsg)           returns (Empty) { option (gorums.unicast)    = true; }
rpc Timeout(TimeoutMsg)     returns (Empty) { option (gorums.multicast)  = true; }
rpc RequestBlock(BlockHash) returns (Block) { option (gorums.quorumcall) = true; }
#+end_example

Votes are *unicast*: DiemBFT 3.1 sends a vote to the leader of the next round
alone, because that leader is the only replica that will propose over the
certificate.

=RequestBlock= is block sync, which section 3 does not specify. A replica that
misses an ancestor cannot speculate, so it holds the block and asks every peer
for the oldest block missing below it (=core.go:insert=). It is a *quorum call*: a unicast has no
reply, and asking every peer means one slow or Byzantine peer cannot hold the
fetch up. The replies are read with =Results()=, and the first block whose
recomputed id is the one asked for, and whose QC verifies, is taken
(=verify.go:VerifyBlock=); =First()= would take the first reply unchecked. The
replica still declines the vote in hand and votes again from the next proposal.
=Safety.DeclinedMissingAncestor()= counts those declines, which is what makes
the gap measurable.

It is not rare. Message *reordering alone*, with nothing dropped and nothing
malformed, is enough to trigger it: Gorums gives per-sender FIFO, but rounds
rotate leaders, so consecutive proposals arrive from different senders on
different handler goroutines. Seeing round r+1's certificate before round r's
proposal is enough to send the replica fetching.

Certificate signature sets travel in strictly increasing signer order. A block
id covers the signature slice byte for byte, so permuting it would change the
id on the receiver and fork the chain; =verify.go= rejects any certificate
that arrives out of it.

No digest from the wire is trusted until the edge has recomputed it. The
=Verifier= requires every hash field to be exactly 32 bytes, and recomputes a
proposal's block id once: the proposer stamps it in =Block.id= because hashing
the payload is expensive, and after =VerifyProposal= the core reads =GetId()=
instead of hashing again.

* Running it

Four replicas in one process:

#+begin_src sh
go run ./cmd/diem -local 4 -time 10s -payload 32 -workers 4
#+end_src

Each replica runs four clients. It prints how many blocks and commands it
committed, its mean propose-to-commit time, how many votes it declined
for a missing ancestor, and how many messages the edge rejected. The =-local=
runs also check that every replica's log agrees over the prefix they share.
